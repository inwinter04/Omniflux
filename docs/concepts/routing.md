# 动态路由与决策留痕

在多模型聚合场景下，如何根据成本、质量、网络延迟和可用性，在多个供应商与模型之间选出最优目标？当目标模型突发故障时，如何保证业务不受影响？

Omniflux 实现了工业级的动态路由引擎与全链路决策留痕机制。

## 路由决策流水线

当业务请求到达数据面的逻辑模型服务时，路由引擎依次执行以下四个处理阶段：

![Omniflux 路由决策流水线](/assets/routing-pipeline.zh-CN.png)

### 阶段 1：硬约束过滤 (Hard Constraints)
首先根据绑定的路由策略规则，强制剔除不符合安全或预算准入条件的候选：
- **供应商黑白名单 (Allowed / Blocked Providers)**：严格限制仅允许调用特定供应商（如仅允许合规国内厂商）。
- **上游模型限制 (Allowed / Blocked Upstream Models)**：拦截未经评测准入的模型标识。
- **混合单价上限**：当候选模型的千 Token 单价超过策略设定的上限阈值时，自动被排除。

### 阶段 2：优先级分组 (Priority Bucketing)
对过滤后保留的候选模型按 `Priority` 字段由小到大排序。
- 路由引擎始终优先在 **数值最小**（最高优先级）的组内挑选主候选。
- 只有当最高优先级的所有候选均不可用或调用全部失败时，才会依次下沉到次优先级组。

### 阶段 3：四维动态综合评分 (4D Dynamic Scoring)
在同一优先级组内，路由引擎根据策略中配置的权重比例（`weights`），对候选模型进行全方位打分：

$$\text{Total Score} = w_c \cdot S_{\text{cost}} + w_q \cdot S_{\text{quality}} + w_l \cdot S_{\text{latency}} + w_r \cdot S_{\text{reliability}}$$

各维度数据来源：
1. **质量分 ($S_{\text{quality}}$)**：结合候选模型配置的基础质效分（`quality_score`，0.0~1.0）及离线 Benchmark 评测基准。
2. **成本分 ($S_{\text{cost}}$)**：基于该模型的 Prompt / Completion 实际单价计算（单价越低，得分越高）。
3. **延迟分 ($S_{\text{latency}}$)**：取自系统近 7 天对该 Provider 模型的真实调用首包耗时与平均响应时长。
4. **可靠性分 ($S_{\text{reliability}}$)**：取自系统近 7 天的平均成功率统计；若近 24 小时内有连续错误，会自动扣减健康权重。

若打分出现并列，则根据候选各自配置的 `weight` 比例进行加权随机选择。

### 阶段 4：自动故障转移链 (Fallback Chain)
综合评分最高的候选作为 **主候选（Primary Target）** 发起请求。
同时，其余评分合格的候选按得分降序被编排进 **Fallback 备用链路**：
- 如果主候选请求返回 5xx 上游错误、触发限频（429）或连接超时，上游网关层将**自动、无感地尝试 Fallback 链中的下一个候选**。
- 支持通过 `fallback_limit` 限制单次请求最大重试次数，防止级联重试雪崩。

## 超时与流式控制策略

- **Provider 超时 (`provider_timeout_ms`)**：控制向上游供应商单次请求的最大等待时间，超时后立即中断连接并切往 Fallback。
- **首包超时控制 (`first_token_timeout_ms`)**：在流式生成（SSE）场景中，若上游已建立连接但在规定毫秒数内未吐出首个 Token，Omniflux 将判定为上游卡顿，主动切断连接并切换候选。

## 决策全量留痕 (PolicyDecision)

在企业合规与排障中，“为什么这笔请求调用了供应商 A 而不是 B”往往至关重要。

Omniflux 会将每次路由评估的中间状态完整存入 `policy_decisions` 记录，包含：
- 请求到达时间与匹配的逻辑模型服务；
- 候选模型被硬约束淘汰的具体原因；
- 候选模型在四个维度的详细得分明细与最终排序；
- 实际命中的主候选与备选 Fallback 链路径。

运维与管理人员可在管理台的「调用明细 → 决策详情」中一键溯源，彻底告别路由调度的“黑盒猜测”。
